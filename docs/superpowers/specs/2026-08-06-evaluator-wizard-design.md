# Add-Evaluator Wizard (QR Invite + Auto-Deactivate) — Design

A new, dedicated flow for creating evaluator accounts: the admin enters an
email and name, optionally flags the account to auto-expire that evening,
and gets a per-evaluator QR code the new evaluator scans to claim their
account and set their own password — no temp password ever shown to them.
Last of four sub-projects split from a larger request (see
`docs/superpowers/specs/2026-08-05-nav-labeling-polish-design.md`'s
"Related items" for the full list; all three prior ones are shipped as
PR #18, #19, #20).

## Problem

Today, `AdminsPage.jsx`'s single "Add User" flow creates either an
Administrator or an Evaluator account, with the admin manually typing a
temp password that gets emailed (or shown on screen if email isn't
configured) for the new hire to log in with and then be forced to change.
This works, but doesn't cover two things GFD wants specifically for
evaluators: a same-day-only account that locks itself out automatically,
and a scan-to-claim flow that skips the temp-password handoff entirely.

## Scope

- A new "+ Add Evaluator" flow, replacing evaluator creation in the
  existing modal (see Change 4).
- A new `evaluatorInvites` Firestore collection, one small library module,
  one new component, one new public page/route, one new npm dependency
  (`qrcode`, for client-side QR image generation — nothing in this repo
  already does this).
- One Firestore security rule change (extending the single existing
  `isActiveUser()` gate) and one new rule block for the new collection.
- No changes to how Administrator accounts are created, to recruit
  accounts, or to any existing evaluator's data.

## Change 1: Auto-deactivate, enforced in the security rules

`firestore.rules` already gates every read/write behind one function:

```
function isActiveUser() {
  return isSignedIn()
    && exists(/databases/$(database)/documents/admins/$(request.auth.uid))
    && myUserDoc().isActive == true;
}
```

Extended to also check a deadline, using Firestore's `request.time`
(evaluated server-side, not the client's clock):

```
function isActiveUser() {
  return isSignedIn()
    && exists(/databases/$(database)/documents/admins/$(request.auth.uid))
    && myUserDoc().isActive == true
    && (!('autoDeactivateAt' in myUserDoc()) || myUserDoc().autoDeactivateAt > request.time);
}
```

Every other rule in the file already calls `isActiveUser()` (directly or
via `isStaff()`/`isAdminRole()`/`isRecruitRole()`), so this one change
blocks all Firestore access for an expired evaluator the instant the
deadline passes — no polling, no reliance on any client being open, no new
Cloud Function. Firebase Auth's own sign-in isn't rules-gated (rules only
govern Firestore), so a stale login could technically still succeed after
the deadline, but every subsequent Firestore read/write fails immediately,
which is the access that actually matters (nothing in this app works
without Firestore).

`admins/{uid}` gains one new optional field: `autoDeactivateAt: Timestamp`,
set only when the wizard's toggle was checked at creation, `18:00` local
time computed as: today's date if the current local time is before 18:00,
otherwise tomorrow's date (so checking the toggle after 6pm never creates
an account that's already expired).

For visible accuracy in the admin's own account list (not required for the
security property above, which the rule already guarantees, but so an
admin isn't confused seeing someone listed as active who can no longer do
anything): `AdminsPage.jsx`'s existing `admins` snapshot listener also
sweeps the loaded list for any account whose `autoDeactivateAt` has passed
and flips `isActive: false` — reusing the same client-side write pattern
`deactivate()` already uses there.

## Change 2: The invite/claim flow

**New collection**, `evaluatorInvites/{token}`:

```
evaluatorInvites/{token} = {
  uid: string,              // the created account's admins/{uid} id
  email: string,
  tempAuthPassword: string, // random, generated by the wizard, never shown to anyone
  used: boolean,
  createdAt: Timestamp,
  expiresAt: Timestamp,     // createdAt + 7 days
}
```

`token` is a `crypto.randomUUID()` (built into every modern browser — no
new dependency), used both as the Firestore document ID and as the path
segment in the claim link. This is the same "an unguessable ID is the
credential" trust model the app already uses for `/live/:token`'s
no-login Live Dashboard — reading a single doc by its exact random ID is
allowed unauthenticated; listing the collection is not, so there's no way
to enumerate or guess a live invite.

`expiresAt` is enforced only by this app's own UI/rules as friction on the claim
button — it is NOT a real security boundary. Firebase Auth sign-in and password
changes are entirely outside what Firestore security rules can govern, so anyone who
reads an invite doc (the `get` is public and unauthenticated, by design, forever) can
sign in directly via the Auth SDK using `tempAuthPassword` and change the password
themselves, bypassing this app's claim page and the `expiresAt` check entirely. The
only real revocation is deactivating the account (the existing Deactivate button,
unaffected by any of this) — an unclaimed invite should be treated as a live
credential to a live account for as long as that account exists and remains
`isActive`, not as something that safely expires on its own.

**Wizard flow** (`AddEvaluatorWizard.jsx`, a new component, opened from a
new "+ Add Evaluator" button on `AdminsPage.jsx`):

1. Admin enters the evaluator's email and display name, and can check
   "Auto-deactivate at 6:00 PM" (helper text: "Deactivates automatically
   at 6:00 PM the day this account is created — or the next day, if
   created after 6:00 PM.").
2. On submit: generate a random temp password (`crypto.randomUUID()`
   again — plenty of entropy, never displayed to anyone), create the
   Firebase Auth account via the existing `createUserAccountWithoutSigningIn`
   helper, write the `admins/{uid}` doc (`role: "evaluator"`,
   `isActive: true`, `mustChangePassword: true` — same shape as today,
   plus `autoDeactivateAt` if the toggle was checked), then create the
   `evaluatorInvites/{token}` doc.
3. The wizard switches to a result screen showing the QR code (rendered
   client-side via the `qrcode` package as a data-URL `<img>`) encoding
   `${window.location.origin}/claim/{token}`, plus the same welcome-email
   attempt/fallback UI `NewUserModal` already has (sent via a new
   `sendEvaluatorInviteEmail` — same EmailJS plumbing and welcome
   template as today's `sendWelcomeEmail`, new plain-text body carrying
   the claim link instead of a temp password).

**Claim page** (`ClaimInvitePage.jsx`, new public route `/claim/:token`,
no login required — same pattern as the existing `/live/:token` route):

1. On load, `getDoc`s `evaluatorInvites/{token}`. Missing, `used: true`,
   or past `expiresAt` all render the same message: "This invite has
   expired or already been used. Ask your administrator for a new one."
2. Otherwise shows the invite's email (read-only) and a "New Password"
   field (6+ characters, matching the minimum length already enforced
   elsewhere in this app).
3. On submit: sign in with the looked-up `tempAuthPassword` (invisible to
   the evaluator throughout), immediately `updatePassword` to what they
   typed, clear `mustChangePassword` on their `admins/{uid}` doc, mark the
   invite `used: true`, sign out, and redirect to `/login` with a
   "Password set — sign in with your new password" message.

**Rules for the new collection:**

```
match /evaluatorInvites/{token} {
  allow get: if true;
  allow list: if false;
  allow create: if isAdminRole();
  allow update: if isSignedIn()
    && request.auth.uid == resource.data.uid
    && resource.data.used == false
    && request.resource.data.diff(resource.data).affectedKeys().hasOnly(['used'])
    && request.resource.data.used == true;
  allow delete: if false;
}
```

## Change 3: Email body for the invite

`web/src/lib/notify.js` gains `buildEvaluatorInviteBody({ toName, claimUrl
})` (mirrors the existing `buildWelcomeBody`, minus any password —
"You've been invited to GFD Recruit Testing as an evaluator. Scan the QR
code your administrator showed you, or open this link to set your
password: {claimUrl}") and `sendEvaluatorInviteEmail({ toEmail, toName,
claimUrl })`, reusing the exact same EmailJS request shape and welcome
template ID `sendWelcomeEmail` already posts to — no new EmailJS
configuration needed. `sendWelcomeEmail`/`buildWelcomeBody` themselves are
unchanged, still used by `NewUserModal` for admin accounts.

## Change 4: `NewUserModal` becomes admin-only

Per the approved decision, evaluator creation moves entirely to the new
wizard — `NewUserModal` stops offering a role choice:

- The "Role" segmented control and its explanatory paragraph are removed.
- `role` state is removed; every write that referenced it uses the literal
  `"admin"`.
- The `notifyOnFailures` field, previously shown only when
  `role === "admin"`, is now always shown (every account this modal
  creates is an admin).
- Modal heading changes from "New User" to "New Administrator"; the
  triggering button on `AdminsPage.jsx` changes from "+ Add User" to
  "+ Add Administrator", sitting alongside the new "+ Add Evaluator"
  button.
- No change to `ROLE_FILTERS`/`ROLE_LABELS` or the account list itself —
  it already shows both roles together and still will; only how each gets
  *created* changes.

## Non-goals

- No "resend invite" or "regenerate QR" affordance if an evaluator loses
  their QR before claiming it — the admin's only recourse today is
  deactivating the stale account and creating a new one. Worth adding
  later if it comes up; not requested now.
- No configurable auto-deactivate time — always 6:00 PM, matching exactly
  what was asked, not a time picker.
- No change to how Administrator or Recruit accounts are created, and no
  change to the `admins` collection's existing fields beyond the one new
  optional `autoDeactivateAt`.
- No Cloud Functions, no scheduled jobs, no change to the free Spark
  hosting plan this app deliberately stays on.
- The claim page's "New Password" field enforces the same 6-character
  minimum as every other password field in this app — no separate
  strength policy.

## Testing

Manual verification (no unit-test framework in `web/`, consistent with
this repo's other recent plans):

1. Open "+ Add Evaluator", fill in email/name, leave auto-deactivate
   unchecked → submit → QR code renders, welcome email attempt shows its
   status (sent, or the manual-fallback text if EmailJS isn't configured
   in this environment).
2. Scan/open the QR's link on a second, unauthenticated browser/device →
   claim page shows the correct email, accepts a new password → submits →
   redirected to `/login` with a success message.
3. Log in with the new password → succeeds, lands on the evaluator's
   normal home screen (not forced into a password-change screen again).
4. Attempt to reload the same claim link after step 2 → shows the
   used/expired message, no way to reclaim.
5. Create a second evaluator with auto-deactivate checked → confirm
   `autoDeactivateAt` is set to today at 18:00 local time (or tomorrow, if
   created after 18:00) — check the raw Firestore value.
6. With a way to simulate/backdate `autoDeactivateAt` into the past
   (e.g., editing the emulator's Firestore data directly), confirm every
   Firestore operation for that account now fails — not just a specific
   page, the underlying rule.
7. Confirm `AdminsPage.jsx`'s list flips that account to inactive
   (disappears from the active list) next time an admin loads the page,
   without anyone clicking Deactivate manually.
8. Open "+ Add Administrator" (renamed from "+ Add User") → confirm no
   role picker, `notifyOnFailures` checkbox always visible, creates an
   admin account exactly as the old flow did for that role.
9. Confirm the evaluator role filter and "See All Users" list are
   unaffected — both roles still show up there identically to before.
